# macOS: инструменты, которые зависают без присмотра

Наблюдалось 2026-09-24 на macOS 26.6.2 с Xcode 27.0, во время ночной работы над ядром.

## Отладчик и символизация ждут разрешения на отладку

**Суть:**
- `lldb --batch … -- <программа>` и `atos -p <pid>` подключаются к живому процессу; без выданного разрешения на отладку они ждут подтверждения и в пакетном режиме висят
- AddressSanitizer, чтобы расшифровать отчёт, сам запускает `atos` против упавшего процесса — и тест висит вместо того, чтобы упасть

**Применение:**
- В сборке ядра с санитайзерами тесты идут с `ASAN_OPTIONS=symbolize=0` (`core/tests/CMakeLists.txt`)
- Адреса из отчёта переводятся офлайн, без подключения к процессу: `xcrun atos -o <бинарь> -arch arm64 -l 0x100000000 <адреса>` — так найдена причина падения на `pipe2` ([freerdp/buildMacOS.md](../freerdp/buildMacOS.md))
- Машинный код функции без отладчика: `xcrun otool -arch arm64 -tV -p <символ> <бинарь>`

## Rosetta может перестать переводить новые программы

**Суть:**
- После запуска x86_64-среза проверки линковки Rosetta перестала переводить любые новые x86_64-программы — даже свежесобранный «hello world»
- Такие процессы висят в состоянии `U` и не снимаются `kill -9`; системный `/usr/bin/true`, у которого перевод уже есть, запускается нормально
- Демон `oahd` (`system/com.apple.oahd`) работает от root, в системном журнале причины не видно
- До этого тот же срез x86_64 проверки линковки запускался без проблем — _причина зависания не установлена_

**Применение:**
- Скрипты сборки запускают код чужой архитектуры через `run_bounded` (`core/scripts/common.sh`) с таймаутом `FOREIGN_RUN_TIMEOUT` и падают с понятной ошибкой, а не висят
- В `build-core.sh` тесты чужих архитектур идут последними: зависшая трансляция не отнимает остальных результатов
- Лечение требует администратора: `sudo launchctl kickstart -k system/com.apple.oahd`, а если не сработает — перезагрузка
- Реальных пользователей это не касается: на Apple Silicon приложение исполняет срез arm64, на Intel — x86_64 без Rosetta
