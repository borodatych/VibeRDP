# RDP: буфер обмена CLIPRDR

Сверено 2026-09-25 на FreeRDP 3.32.0, задача 2.1.
Ядро — `core/src/clipboard.c` и `core/src/cliptext.c`, приложение — `client-macos/Clipboard/ClipboardBridge.swift`.
Устройство моста — решение 25 в [decisions.md](../../decisions.md), приватность буфера macOS — [macos/pasteboardPrivacy.md](../macos/pasteboardPrivacy.md).

## Ход обмена

**Суть:**
- Канал статический, `cliprdr`; клиентская часть FreeRDP грузится при `FreeRDP_RedirectClipboard`, а он у клиента включён по умолчанию (`libfreerdp/core/settings.c:1296`)
- Обмен начинает сервер: Monitor Ready; в ответ клиент шлёт свои возможности и первый список форматов — что лежит в его буфере
- Каждая сторона объявляет только список форматов, а данные идут, когда другая сторона вставляет: Format Data Request и Format Data Response
- На каждый список форматов другая сторона отвечает Format List Response
- В ответе на запрос данных нет номера запроса: ответы идут строго по порядку, и в каждую сторону разумен один вопрос за раз
- Колбэки клиентской части FreeRDP приходят на потоке сессии — там, где разбирается транспорт; отправка из канала через очередь, её можно звать с любого потока
- Пустой список форматов сервера FreeRDP до клиента не доносит: после фильтра по `FreeRDP_ClipboardFeatureMask` пустой список просто отбрасывается (`channels/cliprdr/client/cliprdr_format.c:136-144`)

**Применение:**
- Ядро хранит последнее предложение Мака и шлёт его при каждом Monitor Ready — после переподключения тоже, а до него предложение ждёт
- Вопрос сервера ждёт одного ответа приложения; формат, которого Мак не предлагал, получает отказ сразу, без вопроса
- Копия с сервера одна за раз; если она не дождалась ответа, поздний ответ ждётся и выбрасывается — иначе он достался бы следующей копии

## Текст

**Суть:**
- Windows хранит текст в `CF_UNICODETEXT`: UTF-16LE, строки — CRLF, в конце — нулевой символ; `CF_TEXT` и `CF_OEMTEXT` Windows достраивает из него сама
- Мак — UTF-8 и LF; текст с Windows может нести и одинокий CR, и мусор после нуля

**Применение:**
- Ядро объявляет только `CF_UNICODETEXT`
- Мак → Windows: одинокий LF становится CRLF, CRLF остаётся, в конце — нулевой символ; битый UTF-8 — U+FFFD
- Windows → Мак: текст кончается на первом нуле, CRLF становится LF, одинокий CR остаётся; одинокий суррогат — U+FFFD, нечётный последний байт отбрасывается

## HTML и RTF

**Суть:**
- Оба — зарегистрированные форматы Windows: «HTML Format» и «Rich Text Format»; такие форматы идут по имени, а номер от 0xC000 каждая сторона даёт свой
- Сервер спрашивает данные по номеру, который дал клиент в своём списке, а клиент — по номеру из списка сервера
- «HTML Format» — заголовок из строк `Имя:число`, затем HTML в UTF-8; `StartHTML` и `EndHTML` отмечают страницу, `StartFragment` и `EndFragment` — скопированную часть, её же окружают комментарии `<!--StartFragment-->` и `<!--EndFragment-->`
- Смещения считаются в байтах от начала данных; программа, у которой нет страницы вокруг, пишет `StartHTML:-1`
- RTF Windows хранит с нулём в конце

**Применение:**
- Ядро даёт форматам номера 0xC0A0 и 0xC0A1, а формат сервера узнаёт по имени
- Мак → Windows: метки ставятся вокруг содержимого `<body>`, а HTML без него оборачивается в `<html><body>`; смещения — десятью цифрами, так заголовок пишется раньше, чем они известны, в конце — ноль
- Windows → Мак: берётся страница от `StartHTML` до `EndHTML` — со стилями; без неё — фрагмент; данные без заголовка, которые начинаются как HTML, берутся целиком; смещения за пределами данных — отказ
- RTF идёт как есть: к Windows — с нулём, к Маку — без

## Картинки

**Суть:**
- Windows хранит картинку в `CF_DIB` — растр без первых 14 байт файла `.bmp`: заголовок `BITMAPINFOHEADER`, за ним маски, палитра и строки пикселей, строки снизу вверх при положительной высоте
- `CF_DIBV5` — тот же растр с заголовком `BITMAPV5HEADER` на 124 байта: маски, в том числе маска альфы, и цветовое пространство внутри заголовка
- Из `CF_DIB` Windows сама делает `CF_BITMAP` и `CF_DIBV5`, и наоборот; программе хватает одного из них
- 32 бита с `BI_RGB`: четвёртый байт не альфа, программы Windows оставляют его нулём
- Chromium и Office, по их исходникам и описаниям, пишут рядом зарегистрированный формат «PNG» — с прозрачностью; читают его не все программы; _на Windows не проверено_
- Смещение пикселей в растре не записано: оно считается из размера заголовка, трёх или четырёх масок за `BITMAPINFOHEADER` при `BI_BITFIELDS` и `BI_ALPHABITFIELDS` и размера палитры — `biClrUsed`, а при нуле полная палитра для глубины до 8 бит
- ImageIO читает растр, если приставить к нему 14 байт заголовка файла с этим смещением: палитры, маски, строки сверху вниз и `CF_DIBV5` с альфой проверены тестами
- Изображение ImageIO декодируется лениво и держит данные: буфер, освобождённый до кодирования в PNG, даёт чёрную картинку — поймано тестом на цвет пикселя

**Применение:**
- Приложение говорит с ядром только PNG (`VRCClipboardFormatImage`)
- Мак → Windows: ядро объявляет «PNG» — как есть — и `CF_DIB` — 24 бита, строки снизу вверх, прозрачное поверх белого: программы, читающие `CF_DIB`, альфу не видят, и прозрачное стало бы чёрным
- Windows → Мак: из предложенного берётся «PNG», затем `CF_DIBV5` — может нести альфу, затем `CF_DIB`; растр проверяется — заголовок, маски, палитра и строки должны уместиться в данных — и перекладывается в PNG через ImageIO (`core/src/clipimage.c`)
- Форматы Windows — таблица в `core/src/clipboard.c`: формат приложения, номер, имя, преобразования в обе стороны и порядок предпочтения
- Копия картинки ждёт сервер до 60 секунд — мегабайты по медленному каналу; текст — 10

## Файлы

**Суть:**
- Файлы идут зарегистрированным форматом «FileGroupDescriptorW»: число элементов в 4 байта, затем по 592 байта `FILEDESCRIPTORW` на файл или папку — флаги полей, атрибуты, время записи в `FILETIME`, размер двумя половинами и имя в UTF-16 на 260 знаков с нулём
- Имя — относительный путь через обратную косую черту; папка идёт в списке раньше своего содержимого
- Содержимое — отдельным вопросом File Contents Request: номер файла в списке, размер (`FILECONTENTS_SIZE`, ответ — 8 байт) или диапазон (`FILECONTENTS_RANGE`, позиция в 64 бита и длина); ответ несёт номер вопроса `streamId`, поэтому поздний ответ отличим
- Файлы требуют флагов возможностей `CB_STREAM_FILECLIP_ENABLED`, `CB_FILECLIP_NO_FILE_PATHS`, `CB_HUGE_FILE_SUPPORT_ENABLED`; клиентская часть FreeRDP оставляет только те, что объявил и сервер (`channels/cliprdr/client/cliprdr_main.c:590-610`)
- Длину данных ответа о содержимом FreeRDP кладёт в `cbRequested`, а `dataLen` считает ещё и 4 байта номера — по нему данные не мерить
- `FreeRDP_ClipboardFeatureMask` по умолчанию разрешает файлы в обе стороны

**Применение:**
- Мак → Windows: приложение даёт абсолютные пути, ядро обходит папки (`fts`, ссылки внутри папок и `.DS_Store` пропускаются), строит список с именами от папки, где лежит скопированное, в составной форме Unicode — Windows ждёт её, а на Маке имена бывают разложенными; имя длиннее 259 знаков — отказ всего списка (`core/src/clipfiles.c`)
- Вопросы сервера о содержимом ядро отвечает само, на потоке канала: открывает файл, читает диапазон — до 64 МБ за раз — и закрывает; список остаётся до следующего, так вставка в Windows дочитывает файлы и после нового копирования на Маке
- Windows → Мак: имена списка проверяются — ни пустых частей, ни `.` и `..`, ни ведущей косой черты, иначе отказ всего списка; копия идёт по мегабайту, файлы создаются с `O_EXCL | O_NOFOLLOW` только в свежей папке, время записи ставится из списка
- Список сервера берётся один раз на его копирование: имена верхнего уровня для приложения и файлы для копии — из одного списка, пока сервер не объявил новый
- Блокировку данных (`CB_CAN_LOCK_CLIPDATA`) клиент не объявляет: если во время вставки в Windows скопируют другое, копия на Маке закончится ошибкой

## Сервер-эхо для тестов

**Суть:**
- У sample-сервера FreeRDP своего буфера обмена нет; патч `sample-clipboard.patch` добавляет ему `--clipboard-echo`: сервер по очереди просит у клиента текст, HTML, RTF, `CF_DIB` и файлы из каждого его списка и объявляет их обратно — текст с приставкой `echo: `, остальное как пришло; картинка так проходит PNG → `CF_DIB` → PNG, файлы — списком и содержимым туда, а обратно отдаются по вопросам клиента
- Серверная часть канала — `cliprdr_server_context_new`, возможности и Monitor Ready она шлёт сама (`autoInitializationSequence`)
- Патч идёт последним по имени: он правит те же места `sfreerdp.c`, что `kerberos-nla.patch`, и сделан поверх него

**Применение:** `build-core.sh` и `build-client.sh` запускают сервер-эхо на Unix-сокете; `clipboardEchoTests` в ядре и `testClipboardRoundTrip` в приложении проверяют путь в обе стороны на arm64, под санитайзерами и на x86_64.

**Источники:**
- `core/third_party/FreeRDP/channels/cliprdr/client/cliprdr_main.c`, `cliprdr_format.c`, `include/freerdp/client/cliprdr.h`, `include/freerdp/server/cliprdr.h`, `include/freerdp/channels/cliprdr.h`
- Клиент SDL FreeRDP как образец: `client/SDL/SDL3/sdl_clip.cpp`
