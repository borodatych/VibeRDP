# FreeRDP: sample-сервер как собеседник живых тестов

Проверено 2026-09-25 на FreeRDP 3.32.0 и macOS 26.6.2, задачи 1.2 и 1.3.
Сборка — `core/scripts/build-test-server.sh`, запуск — `client-macos/scripts/build-client.sh`, тесты — `client-macos/Tests/LiveServerTests.swift`.

## Сборка и патчи

**Суть:**
- Сервер собирается из копии исходников подмодуля в `<кэш>/test-server/src`: патчи из `core/scripts/test-server/` накладываются на копию, подмодуль остаётся чистым
- Собирается только `sfreerdp-server`, статически и под архитектуру этого Mac, с Kerberos из той же сборки зависимостей; сертификат и ключ для TLS делаются при каждой сборке и в git не попадают
- Сообщения уровня INFO, например «Listening on», сервер пишет в stdout, а он при выводе в файл буферизуется: готовность сервера на TCP скрипт узнаёт по слушающему сокету (`lsof -sTCP:LISTEN`), а не по журналу
- Сервер FreeRDP запрашивает multitransport по своей настройке, не глядя на то, объявил ли его клиент (`libfreerdp/core/peer.c:956-961`), а настройка по умолчанию включена (`libfreerdp/core/settings.c:1057`); VibeRDP multitransport не объявляет — решение 9 в [decisions.md](../../decisions.md)

**Применение:**
- `multitransport.patch` выключает multitransport у sample-сервера
- `kerberos-nla.patch` добавляет `--kerberos-keytab=<файл>`: с ним сервер пускает только через NLA и только по Kerberos (`AuthenticationPackageList` — `!ntlm`) и слушает TCP на `localhost` — [kerberos.md](kerberos.md)
- `pcap-record-length.patch` чинит проигрыш записи — раздел ниже
- Патч, который перестал накладываться на новый FreeRDP, роняет сборку с именем патча

## Как сервер слушает

**Суть:**
- С `--local-only` сервер открывает только Unix-сокет `<TMPDIR>/tfreerdp-server.<порт>`, TCP-порт не открывается (`server/Sample/sfreerdp.c:1508-1517`); папка — `TMPDIR`, без неё `/tmp` (`winpr/libwinpr/path/shell.c:127-142`)
- Перед `bind` сервер удаляет старый файл по этому пути (`libfreerdp/core/listener.c:279`)
- Клиент FreeRDP принимает имя хоста, начинающееся с `/`, как путь Unix-сокета (`libfreerdp/core/tcp.c:1317-1326`): ядро VibeRDP подключается к нему без доработок
- Иконку `test_icon.*` сервер ищет в папке данных установки и в рабочей папке (`sfreerdp.c:325-345`); установки нет, а сборка кладёт `test_icon.bmp` рядом с бинарником
- Без иконки сервер рвёт клиента сразу после подключения: в журнале `Unable to open test icon` и `PostConnect for peer … failed`
- Каждое подключение получает свой проигрыш записи с начала
- Один процесс либо проигрывает запись, либо отвечает на мышь: путь к записи — общий для всех подключений (`sfreerdp.c:820-837`)

**Применение:**
- `build-client.sh` запускает два сервера из папки сборки — запись на порту 3389 и интерактивный на 3390 — с `TMPDIR` на свою папку из `mktemp -d`: пути сокетов известны заранее и не пересекаются с чужими
- Журналы — `<кэш>/client/results/test-server-replay-<архитектура>.log` и `test-server-interactive-<архитектура>.log`, в CI они уходят вместе с результатами упавшего прогона
- Ожидаемый шум в журналах: перебор форматов иконки до `.bmp`, `Broken pipe`, когда тест отключается посреди записи, и `ERRINFO_LOGOFF_BY_USER` при отключении

## Запись rfx_test.pcap

**Суть:**
- Windows Server 2008 R2, 1024×768, RemoteFX: 60 кадров за 1,4 с в реальном времени
- Кадры 1–6 — чёрный экран
- Кадры 7–12 — бирюзовый экран «Welcome», цвет фона R 28, G 94, B 122
- Кадры 13–56 — рабочий стол с обоями: в левом верхнем углу значки, точка (20, 20) — светло-серая (210, 212, 209); кадр 30 открывает меню «Пуск» слева внизу
- Кадры 57–60 — бирюзовый экран выхода «Please wait for the User Profile Service…»
- Точка (700, 60) с 7-го кадра всегда синяя: бирюзовый фон или небо обоев (93, 173, 246); перестановка байтов делает её бурой или оранжевой

**Применение:** живой тест ждёт 20 кадров и проверяет именно эту точку; угол не годится — к 20-му кадру его закрывает значок «Computer», на этом и падала первая версия теста.

## Интерактивный режим: иконка там, куда показала мышь

**Суть:**
- Без записи сервер заливает рабочий стол серым 160 во всех каналах (`sfreerdp.c:231-268`), а на каждое событие мыши — перемещение, кнопку, extended-кнопку, колесо — стирает прежнюю иконку и рисует её в точке (x + 10, y) (`sfreerdp.c:477-500`, обработчики событий `sfreerdp.c:956-1016`)
- Иконка `test_icon.bmp` — 29×64, фон её того же серого, фигура бирюзовая (110, 183, 200): пиксель (8, 40) иконки отличает её от фона
- В режиме записи иконка не рисуется: `test_peer_draw_icon` выходит при `DumpRemoteFx`
- Горизонтальное колесо и extended mouse sample-сервер объявляет — умолчания FreeRDP (`libfreerdp/core/settings.c:947-948`)
- Клавиши у него почти все без действия, кроме нескольких: G переключает рабочий стол между 800×600 и размером по умолчанию через `DesktopResize`, X закрывает сессию по правилам — с `ERRINFO_LOGOFF_BY_USER` (`sfreerdp.c:882-925`)
- Патч `network-drop.patch` добавляет D: транспорт закрывается без Error Info, как при обрыве сети — [reconnection.md](reconnection.md)

**Применение:**
- Живой тест мыши шлёт перемещение, левый щелчок, кнопку «назад», вертикальное и горизонтальное колесо — каждое в свою точку — и ждёт, пока пиксель (x + 18, y + 40) не станет бирюзовым: так проверяется, что событие дошло до сервера и с верной точкой
- Живой тест клавиатуры нажимает G дважды и ждёт размер кадра 800×600, потом прежний — [keyboardInput.md](keyboardInput.md)
- Живой тест переподключения нажимает D и ждёт, что сессия восстановится и снова примет ввод

## Дефект проигрыша: хвост прошлой записи

**Суть:**
- `tf_peer_dump_rfx` ставит позицию потока в `Stream_Capacity(s)`, а не в длину записи (`sfreerdp.c:581-588`)
- Буфер только растёт, а `update_send_surface_command` шлёт `Stream_GetPosition(s)` байт (`libfreerdp/core/update.c:1481-1500`): каждый пакет уходит с хвостом от прошлых, более длинных записей
- Клиент разбирает настоящую команду, спотыкается о хвост и пишет `unknown cmdType`; сессия выживает — [graphicsOutput.md](graphicsOutput.md), последний раздел

**Применение:** `pcap-record-length.patch` ставит позицию в `record.length`; после него ошибок `unknown cmdType` ноль, а последовательность из 60 кадров не изменилась — проверено пробой, которая пишет пиксели каждого кадра.

## Как устроены живые тесты

**Суть:**
- Серверы запускает скрипт сборки, а не тест внутри приложения: иначе macOS спрашивает пользователя о доступе приложения к съёмному тому и держит запуск до ответа — [macos/removableVolumePrivacy.md](../macos/removableVolumePrivacy.md)
- Тесты получают пути сокетов в `VIBERDP_TEST_SERVER_SOCKET` и `VIBERDP_INTERACTIVE_SERVER_SOCKET` (через `TEST_RUNNER_` у xcodebuild) и подключаются через `SessionController`
- Тест записи ждёт 20 кадров, рисует поверхность в половинном размере через `FrameRenderer` и читает точку назад; тесты ввода — из раздела выше
- Оба затем отключаются и ждут `Disconnected` без единой ошибки: так проверяется и закрытие живой сессии
- Без сервера тесты пропускаются с причиной, тест записи — ещё и без GPU с Metal Performance Shaders; тест записи идёт около 0,6 с, тест ввода — 0,1–0,2 с
