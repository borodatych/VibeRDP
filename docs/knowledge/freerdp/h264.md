# FreeRDP: H.264 через VideoToolbox

Сверено 2026-09-25 на FreeRDP 3.32.0 и macOS 26.6.2, задача 1.11.
Декодер — `core/freerdp/src/libfreerdp/codec/h264_videotoolbox.c`, подключение — `core/freerdp/patches/h264-videotoolbox.patch`, тесты — `h264Tests` в `core/tests`.
Выбор декодера — решение 24 в [decisions.md](../../decisions.md).

## Как FreeRDP подключает декодеры H.264

**Суть:**
- Декодер — «подсистема» `H264_CONTEXT_SUBSYSTEM`: `Init`, `Uninit`, `Decompress`, `Compress` (`libfreerdp/codec/h264.h`)
- Список подсистем задаётся при компиляции (`h264_register_subsystems`, `libfreerdp/codec/h264.c:729-761`), регистрации снаружи нет: свой декодер требует правки FreeRDP
- Есть MediaCodec (Android), Media Foundation (Windows), OpenH264 и FFmpeg; аппаратное ускорение FFmpeg, в том числе VideoToolbox, апстрим помечает экспериментальным (`libfreerdp/codec/CMakeLists.txt:169-173`)
- Имя `WITH_VIDEOTOOLBOX` во FreeRDP занято: это устаревший псевдоним ускорения FFmpeg (`cmake/ConfigOptions.cmake:152-158`) — своя опция называется `WITH_H264_VIDEOTOOLBOX`
- `WITH_GFX_H264` включается, если есть хоть одна подсистема (`CMakeLists.txt:455-459`); без него клиент объявляет серверу `RDPGFX_CAPS_FLAG_AVC_DISABLED`
- `Decompress` отдаёт 1, когда кадр лежит в `pYUVData`, 0 — кадра нет, отрицательное — сбой; `avc420_decompress` на 0 ничего не рисует, на сбое GDI пишет `avc420_decompress failure … ignoring update` и пропускает обновление (`libfreerdp/gdi/gfx.c:738-743`)
- Кадр — три плоскости I420 в `pYUVData` и `iStride`, размер — `YUVWidth` и `YUVHeight`; по ним же проверяются прямоугольники обновления (`h264.c:149-170`)
- У декодера контекст на поверхность RDPGFX; AVC444 гонит основной и вспомогательный кадры через один и тот же контекст (`h264.c:594-620`)

**Применение:** `build-freerdp.sh` собирает FreeRDP из копии подмодуля в `<кэш>/src/freerdp`: поверх копии кладётся `core/freerdp/src`, затем накладываются `core/freerdp/patches/*.patch`; патч, который перестал накладываться, роняет сборку с именем патча.

## Декодер на VideoToolbox

**Суть:**
- Поток приходит в виде Annex B: каждый NAL-блок за стартовым кодом `00 00 01`; нули перед стартовым кодом к блоку не относятся
- SPS и PPS становятся описанием формата — `CMVideoFormatDescriptionCreateFromH264ParameterSets`; новые наборы — новое описание, а сессия, которая его не принимает (`VTDecompressionSessionCanAcceptFormatDescription`), пересоздаётся
- Картинки одного кадра уходят одним сэмплом, каждый блок — за 4-байтовой длиной, как в MP4; разделители AUD пропускаются
- Декодирование синхронное: без флага асинхронности колбэк приходит внутри `VTDecompressionSessionDecodeFrame`, а `WaitForAsynchronousFrames` это гарантирует; буфер сэмпла поэтому переиспользуется
- `kVTInvalidSessionErr` — сессия умерла вместе с декодером, например во сне Мака: создаётся новая, и кадр декодируется ещё раз
- Новой сессии нужен ключевой кадр: P-кадр ссылается на кадры, которых у неё нет; пришлёт ли его Windows после пробуждения — _не проверено_, это шаг 5 раздела 11 [liveChecks.md](../../manuals/liveChecks.md)
- Формат вывода не заказывается: VideoToolbox отдаёт родной, как правило NV12 (`420v` или `420f`), и не пересчитывает ни диапазон, ни матрицу
- Кадр копируется в свои плоскости I420: примитивы YUV → RGB у FreeRDP читают векторами за концом строки и строки за концом кадра, поэтому у плоскостей запас, как у буферов самого FreeRDP — стороны округлены до 16 и ещё 32
- Кадр больше 65535 по стороне отвергается: размеры поверхностей RDPGFX — 16-битные
- Кодер не нужен: клиент только декодирует, `Init` для кодирующего контекста отвечает отказом

**Применение:**
- Ядро включает `FreeRDP_GfxH264` и `FreeRDP_GfxAVC444`: клиент объявляет AVC420 в возможностях 8.1 и AVC444 в 10.x; отдельной настройки AVC444v2 во FreeRDP 3.32 нет — версию выбирает сервер кодом кодека
- Возможности 10.5 и 10.6 FreeRDP объявляет только со сборками масштабирования — cairo или swscale (`channels/rdpgfx/client/rdpgfx_main.c:451-472`); VibeRDP их не объявляет

## Дефект FreeRDP: SSE-сборка AVC444 v1

**Суть:**
- `sse41_ChromaV1ToYUV444` пишет блоки B6 и B7 вспомогательного кадра в чётные столбцы: `_mm_unpacklo_epi8(u, zero)` кладёт значения в чётные байты, а маска `_mm_maskmoveu_si128` выбирает их же (`libfreerdp/primitives/sse/prim_YUV_sse4.1.c:1507-1565`)
- Эталон `general_ChromaV1ToYUV444` и NEON-версия пишут в нечётные — `2 * x + 1` (`prim_YUV.c:162-167`, `neon/prim_YUV_neon.c:684-691`)
- На x86_64 AVC444 v1 из-за этого теряет цветность: в тесте средняя разница 55,75 против 2,34 с универсальными примитивами; AVC444 v2 и arm64 не затронуты
- В master FreeRDP на 2026-09-25 дефект тот же

**Применение:** `core/freerdp/patches/avc444v1-sse-chroma.patch` кладёт значения в нечётные байты и маскирует их; тест `avc444RoundTrip` на x86_64 ловит дефект — после патча 2,34.

## Как проверяется без Windows

**Суть:**
- Потоки делает кодер VideoToolbox: реальное время, без перестановки кадров, профиль High, 40 Мбит/с; YUV для него считает сам FreeRDP — `RGBToYUV420_8u_P3AC4R`, для AVC444 — `RGBToAVC444YUV` и `RGBToAVC444YUVv2`
- Выход кодера — AVCC; тест превращает его в Annex B, как шлёт RDPGFX: ключевому кадру спереди SPS и PPS, каждому блоку — стартовый код
- Декодирование — через публичный API FreeRDP `avc420_decompress` и `avc444_decompress`, то есть через тот же путь, что у клиента, до пикселей BGRX
- Замеры на Apple M4: AVC420 640×480 и 1920×1080 — средняя разница с исходником 1,29 из 255, наибольшая 3–4; AVC444 v1 и v2 — 1,96 и 1,92 на arm64, 2,34 и 2,33 на x86_64; один основной кадр без вспомогательного — 57
- 1080 строк — не целое число макроблоков: поток несёт 1088 с обрезкой, кадр совпадает с исходником и по нижним строкам
- Картинка без наборов параметров и шум вместо картинки — сбой обновления (−1, у VideoToolbox — `-12909`, `kVTVideoDecoderBadDataErr`), следующий ключевой кадр декодируется как обычно

**Применение:** тесты идут на arm64, под санитайзерами и на x86_64; в виртуальной машине CI VideoToolbox может не иметь аппаратного декодера — _программный путь в CI не проверялся на момент записи_.
